    01 / Protocol

    How to study the list

    Reading a solution feels like progress. It isn't. This loop trades coverage for recall — the thing a senior interview actually measures.

    1. 01

      Calibrate on day zero

      Untimed: Two Sum, Valid Parentheses, Merge Intervals. Where you stall tells you what to fix — pattern recognition, Go fluency, or complexity reasoning. Write it down before you plan the weeks.

    2. 02

      Drill one pattern at a time

      Six to eight problems of the same family, back to back, easy → hard. Recognition is what interviews test; random grinding trains memory of specific problems instead.

    3. 03

      Apply the 25-minute rule

      Twenty-five minutes solo, timer visible. Then hints in this order: restate constraints → brute force → name the pattern → pseudocode. Read a full solution only after 45 minutes — and rewrite it closed-book the same day.

    4. 04

      Write compilable Go every time

      Table-driven tests for each solution, go test -race when goroutines are involved, one benchmark per pattern. Never practise in pseudocode; the loop is graded in a compiled language.

    5. 05

      Re-solve on a schedule

      D+3 from a blank file, D+10 against the clock (medium ≤ 20 min), D+30 in a mixed set. Three spaced re-solves beat ten fresh problems.

    6. 06

      Teach it back

      Three minutes out loud: constraints, brute force, insight, complexity, edge cases, Go specifics. Record one a week. Senior loops grade the explanation as much as the code.

    Non-negotiables

    • One problem at a time. Phone in another room.
    • No solution copied without a blank-file rewrite.
    • Log one insight sentence per problem.
    • Keep an error log: bounds, nil maps, slice aliasing, byte vs rune, overflow, goroutine leaks.
    • 20% of every week is re-solving, not new material.
    • Stop adding problems once unseen mediums fall in 25 minutes with tests. Depth beats count.

    The 90-minute block

    • 10Recall yesterday's pattern from memory
    • 35One timed problem: 25 min solve + review
    • 15Compare one optimal solution, write the insight
    • 20Go lab, or re-solve from the error log
    • 10Teach-back out loud, note edge cases

    Minutes. Six days a week. One full mock from week 6 onward.

    02 / Problem track

    The roadmap, easy to hard

    Each phase adds one pattern family and keeps reusing the previous ones. Within a phase, problems run easy → hard; across the track, the ramp goes from array drills to O(1) data-structure design. The list is a menu, not a debt: if a phase's hards are eating the week, bank the mediums and move on.

    Showing all problems

    Links open leetcode.com · progress stays in this browser

    Premium-only problems are deliberately excluded. Every problem here has a free LeetCode page, and every phase ends with at least one problem you should be able to re-solve cold.

    03 / Go track

    The other half of the loop

    Senior Go assessments stop being algorithm quizzes after round one. These are the build-it labs that expose goroutine leaks, lock scope, and allocation habits — the things a LeetCode streak will not teach you.

    0 / — labs shipped · each is a small repo with tests, race detector, and a short README

    Design rounds · rehearse out loud

    45 minutes each, no editor. Sketch the boxes, then defend every box.

    D1

    Rate-limited API gateway

    Per-key token buckets, 429 and Retry-After, hot-key sharding, and where limiter state lives.

    D2

    URL shortener

    Base62 ID generation, read-path caching, collision and expiry strategy, analytics off the hot path.

    D3

    Job queue, at-least-once

    Visibility timeouts, idempotency keys, dead-letter queue, and the ordering guarantees you give up.

    D4

    Metrics pipeline

    Batching, backpressure, cardinality limits, sampling, and when to degrade instead of drop.

    05 / Scorecard

    What the loop actually grades

    Algorithm correctness gets you through the screen. The senior decision is made on the other four rows.

    Problem solving & complexity30%

    Recognises the pattern, proves correctness, states time and space with n defined.

    Go fluency & idioms25%

    Idiomatic slices, maps, interfaces; explicit errors; no panic-driven control flow; allocation awareness.

    Concurrency & runtime20%

    Safe primitives, cancellation, no leaks; scheduler, channels, and GC intuition under pressure.

    Design & tradeoffs15%

    Chooses and defends; names failure modes, backpressure, and what changes at 10× traffic.

    Communication10%

    Thinks aloud, takes hints gracefully, ends with a clear summary and what they would do next.

    Instant downgrades

    • Coding before restating constraints and input size.
    • “It's O(n)” with no variable defined.
    • Swallowing errors with _ to keep moving.
    • Unbounded goroutines, no context, no shutdown path.
    • “I'd use a library” with no design underneath it.
    • Silent debugging for more than two minutes.

    Close every round with

    “Here's the approach, the complexity, the edge cases I tested, and what I'd change at scale.”
